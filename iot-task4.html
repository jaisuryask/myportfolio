A web dashboard for the RAC smart lab

Overview

Tasks 2 and 3 switched a bulb from a dashboard and by voice. Task 4 turns that into a proper application for the Robotics and Automation Club lab. An ESP32 reads a DHT11 (temperature and humidity) and an LDR (ambient light) and writes the values to Firebase. A web page reads the same values live, draws charts, lets an operator set the lab light state and records every reading so it can be reviewed later.

DHT11 + LDR → ESP32 → Firebase Realtime Database → Web dashboard → Operator

Objectives

  • Monitor temperature, humidity and light in near real time.
  • Give the lab one web page for status and control.
  • Show and set the lab light state from the page.
  • Support manual mode and an automatic mode driven by an LDR threshold.
  • Keep a timestamped history of readings and control state.
  • Allow only signed-in users to reach the controls.
  • Export the history as CSV for offline study.

How data moves

  1. The DHT11 gives temperature and humidity to the ESP32.
  2. The LDR gives an analog light value, used for display and for automatic mode.
  3. The ESP32 updates the current branch and adds a record to history.
  4. The web app reads these values and shows them in cards and charts.
  5. In manual mode the operator sets the bulb state ON or OFF from the page, and it is stored in the database.
  6. In automatic mode the intended rule is that the controller compares the LDR value with the saved threshold and decides. Task 5 explains what is and is not in the firmware yet.
  7. The dashboard shows Live while the ESP32 connection is available.

Security and deployment

  • Keep passwords, private keys, service-account credentials and OAuth secrets out of source code and public repositories.
  • Use Firebase Authentication to gate the dashboard.
  • Set Realtime Database security rules so that signed-out users cannot read or change control and sensor data. A web page being signed-in only is not enough if the database itself is open.
  • Prefer per-user or role-based access when several operators will use the lab system.
  • Check the threshold value in both the web app and on the ESP32 so a bad number cannot cause unsafe behaviour.
  • Log important commands and configuration changes so there is an audit trail.
  • Keep database URLs and account identifiers out of shared screenshots.

Next steps

  • Roles such as administrator, staff and student operator.
  • Alert limits and notifications for abnormal readings, sensor faults and lost ESP32 connection.
  • Fail-safe OFF behaviour for the actuator after the connection is lost.
  • Device health: Wi-Fi status, uptime, signal strength and a last-seen time.
  • Charts with a selectable time range and summary cards.
  • Calibration controls for the LDR and the environment sensors.
  • A maintenance log for lab equipment.

In depth: how it really works

This section explains the ideas behind the app: which cloud service does what, how the page stays live, how the data is organised and how automatic mode makes its decision. The report shows the app and its data, not its source code, so the explanations describe how these features normally work and tie each one to what the screenshots show.

What happens from sensor to screen

  1. The ESP32 samples the sensors. The DHT11 gives temperature and humidity. The LDR is read on an analog pin, which on the ESP32 gives a 12-bit number from 0 to 4095. The history reached exactly 4095, the top of that range.
  2. It writes to Firebase. The ESP32 updates the fields under labAutomation/current so the newest reading is always in one place, and adds a record under history with a timestamp.
  3. The database tells the page. The web app does not keep asking for data. It registers a listener on current, and Firebase sends the new values the moment they change. This is why the cards and the Live badge update without a refresh.
  4. The operator acts. Pressing Turn ON writes a new bulb state to the database. To switch the real light, the ESP32 has to read that value and drive the relay. The firmware supplied with the report does not do this yet, which Task 5 documents in detail.
  5. The page shows the stored state. The bulb card changes after the database changes, so what you see is the stored state, not just the button that was pressed. It shows what was requested, and a physical check is needed to confirm the lamp followed.

Cloud terms: IaaS, PaaS, SaaS and BaaS

ModelWhat you manage
IaaSInfrastructure as a service. You rent raw machines, storage and networks and set up everything on top. Maximum control, maximum work.
PaaSPlatform as a service. You supply the code and the provider runs the servers and scaling.
SaaSSoftware as a service. You use a finished application in the browser, with nothing to build.
BaaSBackend as a service. You get ready-made backend pieces, such as sign-in, a database and hosting, and write only the front end. Firebase is this kind of service, and it is the reason this lab app needs no server of its own.

Authentication and authorization

Authentication answers “who are you?” The login page does this with email and password or a Google account. Authorization answers “what may you do?” This is decided by database rules and, later, by roles. The two are separate: someone can be signed in properly and still be forbidden from changing the light. In this prototype the page requires sign-in, and the report advises tightening the database rules so that access is enforced by Firebase itself and not only by the web page.

Why the data has two branches

current is a small, fixed set of fields that is overwritten every time. The dashboard can read it quickly and the ESP32 can update it cheaply. history only grows: each reading becomes a new child with a key that Firebase generates. Keeping a log apart from the latest state means the dashboard never has to search the log to find the current value, and the log is never overwritten, so it can be used as an audit trail and exported.

In the screenshot of the table, new rows appear roughly every 30 seconds, with a gap between 16:07 and 16:55 on the same day. That kind of gap is worth explaining in a real deployment, for example a powered-off board or a lost connection.

Manual and automatic mode

In manual mode the operator owns the light, and the threshold is ignored. In automatic mode the intended design is that the ESP32 compares the LDR value with the saved threshold and sets the relay. The mode is stored in the database, so the dashboard and the history record who is in charge at any moment. The controller can only follow it once the firmware reads the value back.

Which direction counts as dark? That depends on how the LDR is wired in its voltage divider, so a higher number can mean either more or less light. In the three AUTO rows visible in the history table the light was OFF with readings of 2514 to 2758, below the 2800 threshold, but the threshold at that time is not known. It is worth confirming the direction on the bench and writing it on the page.

Flicker near the threshold. The recorded LDR readings average 2877, close to the 2800 setting, and swing by hundreds from sample to sample. With a single hard threshold a reading hovering around 2800 would flip the light on and off repeatedly. A small dead band (switch on below one value, off above a slightly different one) or an average of several readings avoids that.

CSV export

CSV is a plain text table with one record per line and commas between the fields. Because it opens in any spreadsheet, it is the simplest way to take the history out of the app for charts or a lab report. The table columns, timestamp, temperature, humidity, LDR, bulb and mode, map directly to the columns in the file.

Failure cases to design for

  • ESP32 offline. The page can keep showing the last stored values, so a connection badge or a last-seen time is needed to avoid trusting stale data.
  • Open database rules. If anyone can write to the database, anyone can switch the light. The rules, not the page, are the real lock.
  • Bad threshold. A non-numeric or out-of-range value should be rejected both on the page and on the ESP32.
  • Fail-safe. If the connection is lost while the light is on, the controller should have a defined behaviour, such as switching OFF.

Conclusion

The RAC Lab Automation app joins sensing, an ESP32 controller, a cloud database, sign-in, live charts, actuator control and a logged history in one system. The screenshots and the database export agree with each other, which shows data flowing correctly from the sensors to the page. Stronger database rules, roles, alerts and fail-safe behaviour would be the next steps to make it ready for everyday lab use.
